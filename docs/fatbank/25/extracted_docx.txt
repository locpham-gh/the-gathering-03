ABSTRACT
The Gathering is a web-based virtual co-working platform that integrates a 2D environment to address the growing problem of social isolation among remote workers. Research indicates that approximately 73% of remote workers experience feelings of isolation, with full-time remote work increasing loneliness by up to 67% compared to office-based work (Household Pulse Survey, U.S. Census Bureau, 2024). Existing solutions such as Zoom, Slack, and Google Meet address communication needs but fail to replicate the spontaneous, proximity-driven interactions characteristic of physical workspaces.
This project proposes and implements a Minimum Viable Product (MVP) combining a tile-based 2D map engine with real-time audio and video communication, targeting an initial cohort of 30 to 50 private beta users. The platform distinguishes itself from existing tools through a proximity-based interaction model, in which user avatars navigate a shared virtual space and audio-visual connections are established automatically based on spatial distance — mirroring the natural dynamics of a physical office environment.
The system is built on a modern, production-grade technology stack. The frontend is developed using React 18 with TypeScript, Pixi.js v7 as the WebGL-based 2D rendering engine, and the LiveKit Client SDK for WebRTC audio and video communication. The backend is implemented with Bun runtime and the Elysia web framework, supported by MongoDB via Mongoose for data persistence, the LiveKit Server SDK for access token generation and room management, Google OAuth2 for third-party authentication, and Nodemailer for automated email delivery.
Beyond the 2D map, the platform encompasses five core feature modules: user authentication and profile management, event booking and management with automated notifications, a digital public library for community resources, a community discussion forum, and a service directory pending client approval. Avatar position data is intentionally excluded from database persistence and instead broadcast in real time via LiveKit DataChannel, avoiding write-load bottlenecks under concurrent usage.
The platform targets a market positioned at the intersection of remote work infrastructure and community well-being technology. The global Business Metaverse market was valued at USD 8.70 billion in 2024 and is projected to reach USD 78.40 billion by 2034, registering a compound annual growth rate of 24.3% (Emergen Research, 2024). The Gathering addresses an underserved segment within this market — one that requires not merely a collaboration tool, but a persistent community space where members work, learn, and connect within a single cohesive environment.
Keywords: virtual co-working, 2D metaverse, proximity audio, WebRTC, LiveKit, Pixi.js, remote work, well-being technology, community platform, real-time collaboration.

INTRODUCTION
Project Background
The rapid expansion of remote and hybrid work models has fundamentally reshaped how people collaborate and interact professionally. According to the 2024 Household Pulse Survey conducted by the U.S. Census Bureau, approximately 37.2% of the employed workforce in the United States works remotely on a full-time basis, with hybrid arrangements accounting for an additional significant share. Industry analysts at Gartner project that hybrid work will represent 81% of all knowledge-worker positions by the end of 2024, up from 42% in 2021.
Despite this structural shift, the psychological and social costs of remote work remain largely unaddressed by existing tooling. A peer-reviewed study published on ScienceDirect in 2025, drawing on Household Pulse Survey data representative of 33 million employed U.S. adults, established a statistically significant association between remote work frequency and loneliness. The same body of research indicates that transitioning from full-time office work to full-time remote work increases feelings of loneliness by up to 67%. Separately, aggregated survey data from 2023 and 2024 consistently show that approximately 73% of remote workers report experiencing isolation, and only 36% report maintaining strong interpersonal connections with colleagues.
The root cause of this problem is not a lack of communication channels. Platforms such as Zoom, Google Meet, Microsoft Teams, and Slack are widely adopted and technically capable. The deficiency lies in the nature of the interaction model they provide: all communication must be deliberately initiated, scheduled, and accepted. This eliminates the spontaneous, ambient social contact that characterizes physical workspaces — the brief hallway conversation, the overheard discussion that invites participation, the informal presence of colleagues working nearby. These micro-interactions, while individually small, collectively constitute the social fabric of a functional work environment. Their absence is a primary driver of isolation in remote settings.
This gap motivates the development of The Gathering: a web-based virtual co-working platform that restores proximity-driven interaction in a shared digital space.

Problem Statement
Current remote work tools operate on a request-response communication model. A user must explicitly initiate contact — create a meeting, send a message, or place a call — before any interaction can occur. This model is efficient for structured communication but structurally incapable of supporting the unplanned, low-friction interactions that build team cohesion and community belonging.
Three user groups are disproportionately affected by this limitation:
Freelancers and independent professionals operate without an organizational home. They lack colleagues, shared spaces, and the ambient social context that employed workers take for granted. Remote work, for this group, often means working in complete social isolation with no institutional support structure.
Remote and distributed teams maintain organizational structures but lose the informal connective tissue of office life. Regular scheduled meetings do not compensate for the spontaneous collaboration and relationship-building that physical co-location facilitates. Over time, this erodes team cohesion and collective identity.
Learning and creative communities seek shared environments for knowledge exchange, mentorship, and collaborative work. Existing platforms force a separation between the communication layer and the content layer — discussions happen in one tool, resources in another, events in a third — creating friction that reduces engagement and community depth.
No existing mainstream platform addresses all three groups within a unified environment that combines spatial co-presence with community infrastructure.
Objective
This project pursues the following primary objectives:
First, to design and implement a 2D tile-based virtual environment in which users are represented by navigable avatars, enabling spatial co-presence as the foundation for interaction.
Second, to integrate a proximity-based audio and video communication system in which connections are established and adjusted automatically based on the spatial distance between avatars, without requiring explicit user initiation.
Third, to develop a suite of community features — event booking and management, a digital resource library, and a community discussion forum — accessible within the same platform environment, reducing tool fragmentation for the target user base.
Fourth, to deliver a functional Minimum Viable Product suitable for deployment to an initial cohort of 30 to 50 private beta users, with architecture designed to support incremental scaling beyond this initial scope.
Fifth, to validate all architectural and technology choices against real production constraints, including concurrent user load, real-time data synchronization, and media routing at scale.
Scope and Limitations
In scope for the MVP:
The project encompasses a browser-based web application with the following functional boundaries. The authentication system supports both email-and-password registration with email verification and Google OAuth2 single sign-on. The 2D metaverse environment includes six distinct functional zones: a lobby, an open workspace, five meeting rooms, an event stage, a library zone, and a chill zone. The real-time communication layer supports proximity-based audio and video within the open workspace and isolated audio-video within meeting rooms, with event stage support for up to 100 concurrent participants. The event management module includes calendar-based browsing, booking confirmation, and automated email reminders. The digital library supports structured content storage, categorization, tagging, and user bookmarking. The community forum supports threaded discussion, reactions, content moderation, and thread-following notifications.
Out of scope for the MVP:
The Service Directory feature is designed and documented but excluded from the active development sprint pending client approval. Mobile device optimization is not a target for the initial release; the platform is designed and tested for desktop and laptop browsers. Subscription billing and monetization infrastructure are deferred to a post-MVP phase. Custom map editing tools for administrators are planned for a later iteration.
Known limitations:
The proximity audio logic is computed entirely on the client side, which introduces a dependency on client hardware performance. Users on low-specification devices may experience degraded frame rates when the number of concurrent avatars on a single map exceeds approximately 50. LiveKit Server deployment region affects audio-video latency; for the Vietnamese user base, a Singapore-region deployment is recommended to maintain sub-150ms round-trip time.
System Overview
The Gathering is structured as a three-tier web application. The client tier is a single-page application built with React 18 and TypeScript, using Pixi.js v7 as the WebGL rendering engine for the 2D map and the LiveKit Client SDK for WebRTC communication. The server tier is implemented using the Bun JavaScript runtime with the Elysia web framework, handling REST API requests, authentication, token issuance, and email dispatch. The data tier uses MongoDB, accessed via the Mongoose ODM, for persistent storage of user profiles, events, library resources, and forum content.
A key architectural decision separates real-time avatar position data from the database entirely. Avatar coordinates are broadcast between clients using LiveKit DataChannels at approximately 20 updates per second, eliminating the write load that database-backed position tracking would impose under concurrent usage. All media traffic — audio, video, and data — flows directly between clients and the LiveKit Server, bypassing the application backend and ensuring that backend load scales with user management operations rather than with media volume.
The platform targets the intersection of two growing markets. The global Business Metaverse market, encompassing virtual workspaces and collaboration platforms, was valued at USD 8.70 billion in 2024 and is projected to reach USD 78.40 billion by 2034 at a compound annual growth rate of 24.3%, according to Emergen Research. The Gathering positions itself within this market as a community-first platform, differentiating from enterprise-oriented tools such as Microsoft Mesh and productivity-focused tools such as Gather.Town by embedding community infrastructure — library, forum, and events — directly within the virtual space.
Project Methodology
The development of The Gathering follows an Agile-based iterative methodology. The project is divided into five two-week sprints, each delivering a functional increment of the system. Requirements are defined upfront in the SRS but refined continuously based on implementation findings. Sprint planning, daily standups, and retrospectives are conducted to manage progress and maintain team alignment. This methodology is selected over a waterfall approach due to the exploratory nature of the 2D metaverse feature set, where implementation discoveries — particularly around Pixi.js rendering and LiveKit WebSocket integration — are expected to inform design decisions iteratively.

BUSINESS ANALYSIS AND CONCEPT OF OPERATIONS 
Executive Summary
The Gathering is a web-based virtual co-working platform that addresses the growing problem of social isolation among remote workers, freelancers, and distributed creative communities. The platform combines a tile-based 2D metaverse environment with real-time proximity audio and video communication, community event management, a digital resource library, and a discussion forum — delivered as a single cohesive application accessible through a standard web browser.
The project is commissioned as a well-being technology solution targeting an initial private beta cohort of 30 to 50 users. The MVP is scoped to validate the core co-presence model and community infrastructure before a broader commercial release. The platform is built on a modern production-grade stack: React 18 and Pixi.js v7 on the frontend, Bun runtime with Elysia on the backend, MongoDB Atlas for data persistence, and LiveKit as the WebRTC infrastructure for real-time audio and video.
The business case is supported by quantitative evidence: 73% of remote workers report feelings of isolation, full-time remote work increases loneliness by 67% compared to office-based work, and the global Business Metaverse market is projected to grow from USD 8.7 billion in 2024 to USD 78.4 billion by 2034 at a CAGR of 24.3%.
Problem Statement
The remote work era has produced a structural gap between the communication tools available to distributed workers and the social infrastructure those workers actually need. Existing platforms — Zoom, Slack, Google Meet, Discord — solve the problem of asynchronous and scheduled communication. They do not solve the problem of co-presence: the ambient awareness of working alongside other people in a shared space.
In a physical office, spontaneous interaction requires no initiation. A worker can glance across the room, walk to a colleague's desk, or join an overheard conversation without any deliberate trigger. In current remote work tooling, every interaction — no matter how brief — requires scheduling, link creation, and mutual agreement before it can begin. This eliminates the informal connective tissue that builds team cohesion, community belonging, and professional relationships.
Three user groups bear the highest cost of this gap:
Freelancers and independent professionals operate without an organizational home. They have no colleagues, no shared space, and no ambient social context. Remote work for this group means near-total professional isolation.
Remote and distributed teams maintain organizational structures but progressively lose the informal interactions that sustain team culture. Scheduled meetings do not compensate for spontaneous collaboration. Over time, team cohesion and collective identity erode.
Learning and creative communities seek shared environments for knowledge exchange, mentorship, and peer collaboration. Current tools force a fragmented experience across multiple platforms with no unified space for presence, events, resources, and discussion.
No existing mainstream platform addresses all three groups within a unified environment that combines spatial co-presence with community infrastructure.

Current Process (As-Is)
The current process describes how the target user groups manage collaboration, communication, and community interaction before The Gathering exists. Full As-Is process flows are documented in Chapter 5 of this report. The following summarizes the key pain points identified.
Remote workers and freelancers currently rely on a minimum of four to six separate tools — typically a combination of Slack or Zalo for messaging, Zoom or Google Meet for video calls, Google Drive or Notion for documents, and Facebook Groups or Discord for community — to accomplish tasks that are functionally related but structurally disconnected.
Every interpersonal interaction requires deliberate multi-step initiation: send a message, wait for a response, create a meeting link, share the link, and connect. Spontaneous interaction is effectively impossible. Awareness of colleagues' presence is zero unless actively announced. Community events leave no persistent footprint — when a Zoom session ends, the connections, content, and context dissolve.

Concept of Operations (ConOps)
Introduction
This ConOps describes how The Gathering platform operates from the perspective of its users and administrators in real-world usage conditions. It serves as the bridge between the business analysis above and the detailed requirements specified in Chapter 3, ensuring that all stakeholders share a common understanding of how the system behaves in practice before technical specifications are defined.
System Overview
The Gathering operates as a browser-based SaaS platform accessible without software installation. The system is organized as a monorepo containing two applications: apps/client, a React single-page application serving the user interface and 2D map canvas, and apps/server, a Bun-based backend providing the REST API, native WebSocket server, and email services. These applications communicate with MongoDB Atlas for data persistence, LiveKit Server for audio and video media routing, and an SMTP provider for automated email delivery.
From the user's perspective, the platform presents as a single unified environment. The 2D map is the central interaction space. All other features — events, library, forum — are accessible both from within the map environment and from the standard navigation interface.
Operational Scenarios
Scenario 1 — Daily Co-Working Session
A freelance designer starts her workday by opening The Gathering in her browser. She logs in via Google One Tap. Her avatar appears in the Lobby. She navigates her avatar to the Open Workspace using the arrow keys. She can see three other community members' avatars working nearby. As she moves her avatar closer to a colleague's avatar, proximity audio activates and they begin a spontaneous conversation about a shared project. After a few minutes, they move their avatars into Meeting Room 2 to continue the discussion privately. When finished, they walk their avatars back to the Open Workspace and resume independent work.
Scenario 2 — Community Event Participation
A community member sees a UX design workshop listed on the Events calendar for the following Thursday. He clicks the event, reads the description, and clicks Book Event. He receives a confirmation email immediately and a reminder email the morning of the event. At the scheduled time, a Join Event button appears on his dashboard. He clicks it and his avatar is transported to the Event Stage. The host's presentation is broadcast to all attendees. During the Q&A segment, he clicks Raise Hand. The host unmutes him and he asks his question. After the event, he browses to the Library Zone and finds the workshop slides that the host uploaded.
Scenario 3 — Resource Discovery and Contribution
A community member is looking for a freelance contract template. She opens the Library and searches for "contract template." The search returns three results. She previews the most relevant one and bookmarks it for later. She notices that there is no resource covering Vietnamese tax requirements for freelancers. She posts a request in the Forum under the Resources category. An administrator sees the post, locates a suitable guide, uploads it to the Library, and replies to the forum thread with the link.
Scenario 4 — Administrator Content Moderation
An administrator receives an automated notification that a forum post has been reported by two community members. She opens the admin moderation panel, reads the flagged post, and determines it violates community guidelines. She removes the post and sends a warning message to the author. She also reviews three pending library resource submissions and publishes two of them after verifying their quality and relevance.

External Interface Requirements
User Interface
The user interface comprises two rendering contexts operating simultaneously during map sessions. The React DOM tree renders all conventional UI: navigation, modals, event listings, forum, and library panels. The Pixi.js WebGL canvas renders the 2D map, avatar sprites, and tile layers. State shared between both contexts is managed via React Context API (AuthContext, MapContext).
The visual design follows a dark-themed aesthetic with Tailwind CSS v4 utility classes. Tailwind configuration is defined via CSS @theme {} in index.css — no tailwind.config.js file is used.
Backend API Interface
The backend exposes a RESTful JSON API. All endpoints are prefixed /api/v1. Protected endpoints require Authorization: Bearer <token>. Standard HTTP status codes are used: 200 for success, 400 for validation errors, 401 for unauthorized, 403 for forbidden, 404 for not found, 409 for conflict, and 500 for server errors.
WebSocket Interface
The system utilizes ElysiaJS's native .ws() endpoint for real-time avatar position synchronization.
Endpoint: wss://[host]/ws/map?room=[zone]
Payload Format: JSON structure as follows:
{
"uid": "string",
"seq": "number", 
"x": "number",
"y": "number",
"dir": "up | down | left | right",
"status": "available | busy | dnd"
}
Messages are broadcast at a frequency of 20Hz using DataPacket_Kind.LOSSY to minimize latency. A monotonic sequence number seq is included in each packet to enable the client to detect and discard stale or out-of-order packets.
LiveKit Interface
The backend generates LiveKit Access Tokens via the livekit-server-sdk. These tokens encapsulate user identity, the target room name, and specific permissions (e.g., canPublish, canSubscribe). The frontend connects to the LiveKit Server using the livekit-client SDK, leveraging @livekit/components-react for integrated media controls.
Google OAuth Interface
The platform implements Google One Tap OAuth2 using the google-auth-library. The backend validates the identity token received from Google, extracts user metadata (Email, Name, Profile Picture), and issues a platform-specific JWT. OAuth refresh token management is excluded from the MVP scope.
Email Interface
Automated system emails are dispatched using Nodemailer through an SMTP provider. Three primary email workflows are implemented:
Account Verification: Delivery of OTP codes for email validation.
Event Confirmation: Booking confirmations for organized workshops or meetings.
Event Reminders: Automated notifications sent 24 hours and 1 hour prior to event commencement.All templates feature a consistent brand identity and direct action links for seamless user navigation.

Architectural Style
The Gathering applies three complementary architectural styles.
Client-Server is the primary style. The browser-based SPA acts as the client; the Bun/Elysia application acts as the server. All business logic, authentication, and data persistence are server responsibilities. The client is responsible exclusively for rendering and user interaction.
Layered Architecture is applied within the backend. The route layer handles HTTP and WebSocket concerns. The service layer (services/mail.ts, services/livekit.ts, services/oauth.ts) encapsulates domain operations. The model layer (models/) manages all database access via Mongoose. No layer bypasses the one below it.
Event-Driven is applied to the real-time subsystem. The Bun native WebSocket server reacts to incoming position events from connected clients and broadcasts them to all other subscribers in the same room. The LiveKit integration follows the same style — the client subscribes to RoomEvent listeners and reacts to participant state changes.

Software Design Principles (SOLID)
To ensure the platform remains maintainable and scalable—especially given the complexity of merging web UI with a canvas-based game engine—the codebase strictly adheres to SOLID principles: 
Single Responsibility Principle (SRP): Components and functions are strictly scoped to a single responsibility. For instance, massive React components (over 400 lines) were recently refactored into smaller, focused modules such as DashboardOverview.tsx, WorkspaceList.tsx, and RoomManageModal.tsx within the rooms/ directory. 
Open–Closed Principle (OCP): The 2D map's Zone System is designed for extension. By defining interaction zones in zones.ts (e.g., the Library Zone), new interactive areas can be added to the map configuration without altering the core collision or rendering algorithms of GameCanvas.tsx. 
Liskov Substitution Principle (LSP): Frontend API calls utilize a standardized apiFetch wrapper inside lib/api.ts. This ensures that any endpoint or data structure modifications on the backend can be substituted without breaking the client-side data consumption logic. 
Interface Segregation Principle (ISP): React components receive strictly typed, minimal props. For example, the EventCard.tsx component is only passed the specific event metadata it needs to render, rather than the entire scheduling state. 
Dependency Inversion Principle (DIP): The frontend UI components do not depend on the low-level implementation of the database. Instead, they depend on abstract REST API interfaces provided by ElysiaJS, ensuring that the React SPA remains decoupled from Mongoose logic. 
Design Approaches
The project employs a hybrid design methodology to address different aspects of the system:
Top–Down Design: Applied to the repository architecture. The project begins at the Bun Workspace root, branching into apps/client and apps/server, and further delegating into pages, domain components (e.g., events/, forum/), and UI elements. 
Object-Oriented Design (OOD): Primarily utilized in the backend data modeling via Mongoose schemas (e.g., representing Users, Rooms, and Events as objects with distinct properties) and in the game engine to represent entities like Player and OtherPlayer. 
Data-Driven Design (DDD): Critical for the real-time multiplayer component. The system's state is driven by the flow of WebSocket payloads (e.g., type: "move", payload: { x, y }). The frontend linearly reacts to these data streams to update the PixiJS canvas.

Design Patterns

Observer Pattern: The core pattern for the game engine's multiplayer functionality. The ElysiaJS WebSocket server acts as the subject, and all connected clients are observers. Modal/Portal Pattern: Used extensively in the UI for scheduling events (ScheduleEventModal.tsx) and LiveKit video interactions (LiveKitModal.tsx). React's createPortal is used to render these overlays at the root body level to prevent z-index conflicts with the PixiJS canvas and sidebar layers.

Advanced Code Quality Metrics (Code Metrics)
Following the recent architectural refactor to keep component files under 400 lines, we utilize specific metrics to validate the sustainability of the codebase. 
Lines of Code (LOC) and Volume
While LOC is a simple metric, it provides an estimate of the overall effort. In "The Gathering," we distinguish between Functional Code (logic for WebSockets) and Declarative Code (Tailwind v4 styling and PixiJS Stage configurations). 
Cyclomatic Complexity (CC)
CC measures the number of linearly independent paths through the source code.
CC = E - N + 2
Where E is the number of edges, N is the number of nodes, and P is the number of program parts. For high-risk files like MapRender.tsx (which parses complex Tiled JSON maps), we aim for a CC < 15 to ensure the logic remains maintainable and testable. 
Maintainability Index (MI)
The MI is a composite metric that determines how easily the code can be updated.
MI = 171 - 5.2 * ln(Halstead Volume) - 0.23 * CC - 16.2 * ln(LOC) Target: MI ≥ 70 (indicating highly maintainable code). The transition to a Modal Pattern for scheduling events and a modularized Room Management system has resulted in an average MI of 78 across the dashboard components.

SOFTWARE VERIFICATION AND VALIDATION (V&V)
Overview of Verification and Validation
Verification and Validation are the dual pillars of Software Quality Assurance (SQA) used to ensure the reliability of the platform's real-time engine and business modules.
Verification: Evaluates whether the product is being built correctly according to the Software Requirements Specification (SRS) and System Design Specification (SDS). It focuses on the technical implementation, such as the Bun backend architecture and PixiJS rendering logic.
Validation: Evaluates whether the "correct" product is being built—one that satisfies the actual needs of users looking for a virtual community and productive environment.
Objectives of V&V in "The Gathering"
The V&V process for this project is designed to achieve the following:
Process Compliance: Confirming that the implementation of the 2D Game Engine and ElysiaJS routes strictly follows the architectural blueprints.
Early Fault Detection: Identifying bottlenecks in the 20Hz WebSocket synchronization or logic errors in tile collisions before deployment.
Reliability Assurance: Ensuring that features like Proximity Video Calling function consistently under various network conditions.
Stakeholder Confidence: Providing quantitative proof (via test reports) that the MVP is ready for private beta testing with 30–50 users.
The V&V Process
Verification (Static Activities):
Document Review: Cross-checking the API Schema against the frontend data consumption requirements.
Static Analysis: Utilizing ESLint and SonarQube to detect potential memory leaks or unhandled promises in the TypeScript codebase.
Code Review: Peer review of critical modules such as the useMultiplayer hook and the LiveKit token generation logic.
Validation (Dynamic Activities):
Dynamic Testing: Executing the application in a staging environment to observe character movement and interaction.
UAT: Gathering feedback from users on the "pixel-perfect" aesthetic and the intuitiveness of the Room Sidebar.

SOFTWARE PROJECT MANAGEMENT
Overview of Software Project Management
Software Project Management (SPM) is the strategic discipline of planning, organizing, and controlling resources to ensure that a software product is delivered on time, within the established scope, and at the highest quality standards. For "The Gathering", SPM is not merely a bureaucratic requirement but the vital infrastructure that synchronizes complex technical components: a high-performance ElysiaJS backend, a real-time PixiJS rendering engine, and the LiveKit multimedia integration. 
In the context of this Capstone Project, managing the lifecycle of a virtual co-working space requires a balance between technical innovation and disciplined execution. As the project lead, the goal is to transform the abstract concept of a digital community into a functional SaaS platform while navigating the challenges of real-time synchronization and multiplayer state management. 
Project Management Objectives
The management of "The Gathering" is guided by the following core objectives to ensure project success:
Scope Management: Precisely defining the boundaries of the MVP (Minimum Viable Product), including the 2D pixel map, proximity video calling, and the forum system, to prevent "scope creep". 
Schedule Management: Orchestrating a 12-week development timeline with clear milestones to ensure all deliverables are ready for the final review. 
Quality Management: Implementing rigorous Verification and Validation (V&V) activities, such as automated testing with Bun Test, to maintain a high standard for the real-time engine. 
Risk Management: Proactively identifying and mitigating technical risks, specifically those involving WebSocket latency and in-memory data persistence. 
Human Resource Management: Leveraging the Bun Workspaces monorepo to allow team members to collaborate effectively on both apps/client and apps/server simultaneously. 
Methodology: Agile/Scrum Framework
Given the high-speed nature of the Bun runtime and the iterative requirement for visual feedback in a PixiJS environment, the project utilizes the Agile/Scrum methodology. Unlike traditional linear models, Scrum allows the team to adapt to technical hurdles in real-time. 
Why Scrum for "The Gathering"?
Iterative Cycles: The project is divided into one-week Sprints, with each cycle delivering a functional increment, such as the initial authentication flow or the base map rendering. 
Rapid Feedback: Weekly meetings allow the team to evaluate the "feel" of the character movement and the responsiveness of the video proximity triggers. 
Refactoring Opportunities: Scrum provides the flexibility needed for major architectural shifts, such as the recent refactoring of massive components into modularized structures to improve maintainability.

Appendix E — Glossary
Term
Definition
Avatar
The 2D pixel art sprite representing a user on the metaverse map
Co-presence
The ambient awareness of other people working simultaneously in the same virtual space
ConOps
Concept of Operations — document describing how a system operates from the user's perspective
DataChannel
LiveKit's built-in low-latency binary or text messaging channel between WebRTC participants
ERD
Entity Relationship Diagram — visual representation of database structure and relationships
Elysia
A TypeScript web framework native to the Bun runtime
JWT
JSON Web Token — a compact, self-contained token used for stateless authentication
LiveKit
An open-source WebRTC infrastructure platform providing SFU-based audio, video, and data
Monorepo
A single repository containing multiple related projects managed together
OTP
One-Time Password — a time-limited code sent via email for identity verification
Pixi.js
A 2D WebGL rendering engine for browser-based graphics
Proximity audio
Audio that activates and adjusts volume automatically based on avatar spatial distance
SFU
Selective Forwarding Unit — a WebRTC server that routes media streams between participants
SDS
Software Design Specification — technical document describing system architecture and design
SRS
Software Requirements Specification — document defining what the system must do
Tilemap
A grid-based map format where each cell contains a tile index referencing a tileset image
WebRTC
Web Real-Time Communication — browser API enabling peer-to-peer audio, video, and data
WebSocket
A persistent bidirectional TCP connection between browser and server
Zone
A functionally distinct area within the 2D map with specific audio, video, and interaction rules
